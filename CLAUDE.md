# Ovilog — règles du projet

## Exports PDF
(Voir aussi la section « Charte graphique » ci-dessous : elle fait foi pour la forme de tous les PDF.)
Tout PDF généré par Ovilog doit être beau, coloré et jovial, avec une charte unique : bandeau vert Ovilog, tuiles et pastilles colorées, mêmes couleurs et même mise en page partout. Un export disponible sur PC et sur mobile produit exactement le même PDF des deux côtés. Pas de PDF en noir et blanc sobre. Références : maquettes "Export PDF" Qualité, Rapport de campagne, Déclaration annuelle. Il n'y a plus d'export PDF « Tank » : seul le Calendrier du tank existe (« Export PDF » vert et « Export Excel » blanc, sur PC comme sur mobile).

Décisions communes à tous les PDF :
- Pied de page unique : « Ovilog — [export] · [campagne] » à gauche, « Page X/Y » à droite (`pdfPied`) ; « Année » à la place de la campagne pour la Déclaration.
- Le nom de l'exploitation est lu par une seule fonction, `pdfExploitationNom` (repli « Ovilog » si vide) : aucun PDF ne le lit autrement.
- En-têtes de tableau jamais coupés : la police diminue avant toute coupure.
- Contrôle laitier (PDF et Excel, comme l'écran) : colonnes N° court, Date de mise bas, C1, C2, C3, dans cet ordre, sans colonne cumul (le champ `cumul` reste dans le modèle).

## Charte graphique
Référence unique pour tout nouvel écran et tout PDF. PC, mobile et PDF ont le même style. Interdiction de revenir à l'ancien style gris. Aucune couleur n'est écrite en dur hors des variables CSS (`--ch-*` dans le `:root`) et des constantes PDF (`PDF_CHARTE`, `PDF_COULEURS`) : on utilise la variable, on n'écrit pas la valeur. Chaque refonte la respecte, sans réinventer.

### Couleurs
- Fond de page : #fbf8f1 (crème). Cartes : blanc #ffffff, bord #e6ddc9, rayon 18 px (14 px sur PC).
- Texte : #2b261c. Texte secondaire : #5e5b47. Icônes/chevrons : #8a8670.
- Vert Ovilog (en-tête, bouton principal) : #357f4b. Vert foncé (texte, chiffres, 1re colonne) : #2f6e44. Vert pastel : #e3f3e6 (texte #24613a).
- Bleu : #1f5a8a, pastel #e6f0fa. Ambre : #b5701c, pastel #fbeed7 (texte des pastilles ambre #8a5413, variable `--ch-ambre-texte`). Rouge : #a33a31, pastel #fbe3e0.
- Fond segmenté/onglets : #efe9da. Ligne alternée de tableau : #f6f1e4. Séparateur : #efe9da. Bord de champ : #d9cfb8.

### Composants
- Police Roboto, chiffres tabulaires.
- En-tête d'écran : bandeau vert #357f4b, OVILOG centré, nom de l'éleveur à gauche, campagne à droite, titre de l'écran dessous.
- Onglets : pastille blanche sur fond #efe9da, arrondie.
- Tuiles d'effectifs (mobile) : fond pastel, liseré gauche épais coloré (5-6 px), libellé gris, grand chiffre coloré. Vert, bleu, ambre, rouge selon le sens.
- Tuile PC unique (`.tuile-pc`, même composant sur tous les écrans PC, Accueil compris) : liseré gauche 5 px, fond pastel, libellé gris 13 px en minuscules, chiffre 24 px gras. On n'invente pas de variante de tuile.
- Tons des tuiles, par sens : vert = bon ou neutre positif, bleu = information, ambre = à surveiller, rouge = SEULEMENT une alerte avérée (jamais pour un simple zéro), neutre (gris) pour un résultat vide ou « — ». Une seule fonction, `tonTuile(valeur, ton, neutreAZero)`, pour l'écran et le PDF (`pdfTuile`) : vide ou « — » → neutre, rouge à 0 → neutre ; « Sous délai d'attente » rouge (neutre à 0), « Vide » ambre, « Vide définitive » rouge (neutre à 0).
- Tableaux : en-tête vert #357f4b texte blanc gras, lignes alternées blanc / #f6f1e4, 1re colonne en vert foncé gras, coins arrondis.
- Boutons : principal = pastille verte pleine, texte blanc ; secondaire = pastille blanche à contour #d9cfb8. Hauteur 44-48 px (sur mobile, tout `.btn` fait au moins 44 px ; un bouton « + » à côté d'un champ prend la hauteur du champ ; un petit bouton de ligne relevé à 44 px — Modifier / Suppr., Retirer — reste une pilule avec 16 px de marge latérale, texte inchangé). Jamais de fond rouge, ambre, bleu ou marron (« Démarrer la campagne », « Valider… », Vendu : vert). Le rouge n'existe qu'en bouton secondaire `.btn-supprimer` (contour et texte rouges) et seulement pour une suppression définitive (Supprimer, Suppr., Retirer, Nettoyer le registre, application du dédoublonnage) ; Annuler, Vider, Vendre, Mort, Restaurer… restent des boutons secondaires normaux.
- Pastilles d'état : arrondies, pastel + texte foncé (Entrée vert, Morte rouge, Vendue bleu). Femelle ambre ; Réforme et compteurs d'onglet neutres ; anomalies du contrôle laitier et `.reg-pastille.rouge-clair` en ambre. Icônes : `.ic-coral` est neutre ; une vraie alerte prend `.ic-alerte` (rouge, ex. « Agnelage déjà enregistré »).
- Focus : cadre vert charte partout (champs : bord vert + halo pastel ; boutons, liens, cases : contour vert 2 px). Jamais d'orange ni de cadre par défaut du navigateur.
- Connexion, lecture du compte et première configuration : ni en-tête ni menu latéral (PC compris, classe `porte-auth` sur `body`), contenu centré.
- Un seul titre par écran PC : celui du bandeau vert. On ne le répète pas dans le contenu, ni en sous-titre d'une carte qui porte déjà ce titre.
- Libellés d'export identiques partout : « Export Excel » (bouton blanc) puis « Export PDF » (bouton vert).
- Pas de scan sur PC : aucun libellé « Scanner » ni « bip » (champs « Saisir un n° » / « Saisir un n° / EID », saisie clavier de l'EID) ; le scan reste sur mobile.
- Lecteur Bluetooth (mobile) : état jamais rouge (vert = connecté, ambre = reconnexion ou absent), pastille (36 px) présente sur TOUS les écrans mobiles à bandeau vert, en haut à droite sur la ligne du logo, symétrique du bouton menu (absente sur PC, sans plugin Bluetooth et sur Paramètres › Lecteur) : libellés courts « Lecteur » (vert), « Connecter » (ambre), « Choisir » (ambre), « Connexion… » / « Reconnexion… » (ambre) ; toucher sur « Connecter » = connexion immédiate sans quitter l'écran ; toucher sur la verte, sur « Choisir » ou appui long = écran Lecteur ouvert PAR-DESSUS l'écran courant (la saisie en cours n'est jamais perdue) ; la saisie manuelle reste toujours possible. Réglages du lecteur (reconnexion automatique, bip) propres à l'appareil, jamais synchronisés ; le bip coupe tous les bips et les quatre bips (trouvé, ambigu, introuvable, déjà trouvé) restent distincts. PC : une seule ligne « Lecteur : mobile uniquement » dans Paramètres.
- Saisies (mise bas, échos, mouvements…) : annuler une saisie se fait en UN geste, sans `confirm()` ; les contrôles sont discrets (aucun encart permanent, un message seulement quand une règle se déclenche : bloquer l'erreur certaine, alerter le doute). Sur mobile : tuiles de la charte (`.tuile-charte`), barre fixe « Annuler | Enregistrer et suivante ». Numéro d'un agneau né dans l'élevage (fiche brebis, saisie rapide mobile et PC) : on peut taper seulement les 5 derniers chiffres (ex. 71001) ou le numéro national (000121 71001), l'EID complet est reconstitué (« 2500 » + indicatif de marquage de l'exploitation + n° individuel) par `resoudreEidAgneau`, jamais ailleurs ; l'indicatif est affiché grisé devant le champ (« FR 000456 », `champEidAgneauHtml`, affichage seul) et disparaît dès qu'un n° complet est bippé ou tapé (agneau d'un autre élevage : son n° national complet est gardé tel quel) ; un EID bippé ou une saisie libre reste tel quel ; sans indicatif à 6 chiffres, erreur claire et rien de deviné ; le chiffre d'année du n° est comparé à la CAMPAGNE de naissance (nommée par son année de fin : né en novembre 2026 = campagne 2027 = boucle en 7) et l'année civile de naissance est aussi acceptée ; s'il ne colle à aucune des deux, c'est une alerte (`apercuEidAgneau`), jamais un blocage.
- N° de boucle suivant proposé à la mise bas (saisies rapides mobile et PC, fiche brebis : `numeroBoucleSuivant`) : la case du n° de chaque NOUVEL agneau vivant est pré-remplie avec le plus grand n° individuel des agneaux de la CAMPAGNE en cours (indicatif de l'élevage) et de ceux déjà saisis dans la mise bas, + 1, en sautant un n° déjà pris sous toute forme (`conflitEidToutesFormes`) ; rien sans indicatif ni avant le premier agneau bouclé à la main (il sert de départ) ; une boucle sautée se corrige à la main et la suite repart de là ; jamais pour un mort-né ni pour un agneau déjà enregistré ; un bip remplace la proposition ; rien n'est réservé avant « Enregistrer ». Réglage de COMPTE « Proposer le n° de boucle suivant » (Paramètres › Règles d'élevage › Mises bas, `boucleSuivanteAuto`, dans `META_FIELDS`, absent = actif). Numérotation séparée mâles / femelles : plus tard. Contrôle : `test_boucle_suivante`.
- Identifier les agneaux (MOBILE seulement, `renderIdentifierAgneaux`) : agneaux nés sans n° (ni mort-nés, ni sortis : `agneauxSansNumero`) retrouvés par le n° de la MÈRE (5 derniers chiffres, n° de travail ou EID tapé ou bippé, `porteesAIdentifier`), jamais par un repère peint ; accès par la tuile ambre « Agneaux sans n° · Identifier » de l'écran Mises-bas (seulement s'il y en a, aucune ligne de menu). Portée : agneau choisi d'office seulement s'il est seul ; n° suivant proposé (`numeroBoucleSuivant`) ; mêmes règles qu'à la mise bas (`resoudreEidAgneau` : vieille boucle tapée = alerte ambre, jamais un blocage ; EID bippé pris tel quel, jamais bloqué ; n° déjà porté par un animal sous toute forme = blocage, `conflitEidToutesFormes`). « Enregistrer et suivant » (`identifierAgneau`) : n°, entrée « Naissance » datée de la mise bas, soins au bouclage ; le soin déjà fait et le père de l'IA restent sur l'agneau. Un bip remplit la case sans enregistrer. Bandeau 6 s « n°… identifié · Annuler » au-dessus de la barre (jamais par-dessus) : fiche exacte d'avant (`annulerIdentificationAgneau`), sans `confirm()`. Sur l'agneau choisi : sexe corrigeable (Mâle | Femelle) et « Adopté par une autre mère » (n° ou EID d'une brebis ACTIVE, jamais sa propre mère ; adoption déjà notée = interrupteur allumé, l'éteindre la retire), écrits seulement avec le n° (`identifierAgneau(…, opts)`) ; « Mort sans n° » (`declarerMortAgneauSansNumero` : fenêtre du bas, date du jour, ni avant la mise bas ni future, cause facultative de la liste des agneaux) : l'agneau quitte « Sans n° » sans compter dans « Identifiés », bandeau « … mort · Annuler » = fiche exacte d'avant ; aucune entrée « Naissance » (jamais bouclé). PC : rien. Contrôles : `test_identifier_agneaux`, `test_identifier_ajouts`.
- Écran Mises-bas (saisie rapide mobile et PC) : liste de TOUTES les mises bas de la campagne (mobile : plus de limite, cartes à faire défiler ; PC : 10 puis « Voir toutes »), dans l'ORDRE D'ENREGISTREMENT, la dernière saisie en haut (`misebasCampagneRows`) : chaque nouvelle mise bas porte l'instant de sa saisie à la milliseconde (`agnelage.saisieA`, posé par `enregistrerMiseBas` et la fiche brebis à la création ; une modification le garde) ; les mises bas d'avant cet horodatage viennent après, date la plus récente puis n° croissant (rien n'est inventé). Contrôle : `test_misebas_ordre_saisie`.
- Synchro pendant une saisie : sur un écran de saisie dont le formulaire ne vit qu'à l'écran (`add-*`, `edit-*`, mises bas rapides, échos rapides : `vueDeSaisieEnCours`), une donnée reçue d'un autre appareil est appliquée tout de suite à DB et au stockage local, mais l'écran n'est JAMAIS reconstruit (sinon le formulaire repart à zéro sous les doigts) ; il se rafraîchit à l'enregistrement ou au changement d'écran. Ailleurs, le redessin garde la saisie en cours, champs sans id compris (repérés par classe + data-id).
- PC (Electron, Windows) : après chaque `alert()` / `confirm()`, le focus clavier est rendu à la fenêtre (`electronAPI.refocus`, bug Electron des champs qui ne reçoivent plus la frappe). Ne pas contourner ce rappel ; ne pas ajouter de nouvelle boîte native dans une saisie (règle « sans `confirm()` » ci-dessus).
- Aucun soin ajouté d'office à la naissance sans réglage de l'éleveur (plus de Séléphérol automatique ; compte neuf : aucun produit, donc aucun soin au bouclage) : un soin se saisit par le Carnet sanitaire, avec un produit créé par l'éleveur (soin collectif possible sur les agneaux). Les anciens soins Séléphérol restent intacts (registre) ; un ancien soin sans copie de délais est lu d'après la fiche produit, à l'affichage seulement. Contrôle : `test_neutralite`.
- Soins au bouclage des agneaux : réglés sur la FICHE PRODUIT (Produits et délais, `ouvrirFicheProduitModal`, case « Donné à chaque agneau au bouclage » ; dose obligatoire et voie affichées seulement si la case est cochée ; `produitsInfo[nom].bouclage` { doseCc, voie }, synchronisé avec `produitsInfo` ; pastille « Au bouclage · 2 cc » dans la liste ; plus de carte dans Paramètres, l'ancienne liste de compte `soinsBouclage` est reprise une fois sur les fiches par `migrateData`), produit de Produits et délais avec délais lait et viande renseignés. Chaque agneau qui reçoit son n° à la saisie de la mise bas (saisies rapides mobile et PC : `enregistrerMiseBas` ; fiche brebis, création et modification) reçoit ces soins datés de la mise bas, construits comme un soin du Carnet (`appliquerSoinsBouclage`, `soinBouclage` : délais de la fiche figés, intervenant « Éleveur », `bouclage: true`) : fiche, Carnet, registre, modifiables et supprimables. Jamais rétroactif (agneau déjà bouclé, réglage ajouté après coup), jamais pour un mort-né. Aucun message à chaque bouclage : une seule ligne grise fixe « Au bouclage : Séléphérol 2 cc » sur l'écran de saisie (`ligneSoinsBouclageHtml`). Retirer le réglage ne touche aucun soin déjà donné. Contrôle : `test_soins_bouclage`.
- Soin sur un agneau pas encore bouclé (Carnet sanitaire, mobile et PC) : les agneaux sans n° (ni mort-nés, ni sortis : `agneauxSansNumero`) sont proposés par leur mère, « Mâle de n°69002 (sans n°) » (`libelleAgneauSansNumero`, retrouvés aussi par le n° de la mère) ; le soin va sur la fiche de l'agneau et le suit au bouclage (Identifier les agneaux, Modifier l'agnelage, tri : même fiche). Référence INTERNE `lamb.ref` (« AG-… ») posée au premier soin seulement, jamais affichée ni prise pour un n° (le champ eid reste vide) ; avant, clé de position `sansn:` (affichage seul, rien d'écrit) ; `animalActuelParEid` les retrouve (`agneauParCleSansNumero`) : annulation du lot, soin collectif et sa suppression compris. Ne se bipe pas, n'entre jamais dans un lot. Sous délai d'attente (onglet Agneaux, délai viande) et registre sanitaire (écran, Excel, PDF : `numeroLigneSanitaire`) : « Mâle de n°… (sans n°) » jusqu'au bouclage, puis le n° de l'agneau. Contrôle : `test_soin_agneau_sans_numero`.
- Carnet sanitaire, n° des animaux (PC et mobile) : MÊME correspondance que l'Accueil (`numerosRechercheAnimal` : EID, 5 derniers chiffres, n° de travail SIEOL court et long, n° de travail du bélier ; par morceau, sans espaces ni casse) ; un agneau sans n° est retrouvé par TOUS les n° de sa MÈRE. N° tapé puis OK / Entrée, ou bippé (`resoudreNumeroCarnet`, contre tous les animaux éligibles) : EID ou n° national = l'animal bippé, jamais ses agneaux ; n° court exact (zéros de tête ignorés) : un seul = coché (champ vidé, curseur gardé), plusieurs (ex. la brebis et ses agneaux sans n°) = liste réduite à eux, rien d'office, le choix touché ramène la liste complète ; aucun = message ambre. Contrôle : `test_carnet_numeros`.
- Carnet sanitaire en ONGLETS (PC et mobile) : Nouveau soin | Soins réalisés | Sous délai | Produits | Ordonnances (`carnetOnglet`, `carnetOngletsHtml`, `ongletCarnetDeVue`). Nouveau soin = le parcours en deux étapes SEUL (plus de « Derniers soins » ni « En délai d'attente » dessous). Soins réalisés (`ongletSoinsRealises`) = tous les soins : animaux présents (agneaux sans n° compris) et animaux sortis en lecture seule, pastille « Sorti », sans Modifier / Suppr. (`soinsRealisesSortis`, lignes du registre), du plus récent au plus ancien, un collectif sur une ligne, 30 puis « Voir tous les soins » ; filtres n° (même recherche que partout, agneau sans n° par sa mère), période du… au…, type, produit, catégories (`soinsRealisesCarnet`) ; « Traitements sur 12 mois » (bio) et « Anciens traitements collectifs » en tête ; en bas Export Excel puis Export PDF qui suivent les filtres (lignes du registre sanitaire, `lignesSanitaireSoinsRealises`), sans filtre = tout le registre sanitaire. Sous délai, Produits et Ordonnances sont les écrans existants ouverts avec la rangée d'onglets quand on vient du Carnet (écran de tête : menu, pas de retour, titre « Carnet sanitaire », `poserOngletsCarnet`) ; ouverts d'ailleurs (Accueil › Sous délai, Paramètres › Listes › Produits) : écran d'avant, retour d'origine, pas d'onglets. Écran 2 (choix des animaux) : millésimes à cocher, plusieurs possibles (`millesimesExclus`, tous cochés au départ) ; lot Tous | Dans le lot | Hors du lot | Aucun lot (`lotCorrespondCarnet`) : les listes automatiques (`lot.auto` : Attendues à la traite, À passer à l'écho…) ne comptent jamais comme un lot (`lotsReels`). Contrôle : `test_carnet_onglets`.
- Carnet sanitaire, corriger un soin (PC et mobile) : l'onglet « Soins réalisés » porte « Modifier » et « Suppr. » sur CHAQUE soin, agneau sans n° compris ; traitement collectif : « Modifier » = toutes ses copies et son historique (`DB.traitementsCollectifs`), « Animaux » › « Retirer » = un seul animal, « Suppr. » = tout le lot. Soin relu au moment du geste (`localiserSoinCarnet`, vérifié par son contenu ; changé = rien n'est fait). Suppression en UN geste, sans `confirm()`, bandeau 6 s « … supprimé · Annuler » = soins et historique exacts d'avant (`supprimerSoinsCarnet`, `restaurerSoinsCarnet`). Modifier retire du soin un champ vidé dans le formulaire (`soinModifie`). Supprimer un soin depuis la fiche (glisser, inchangé pour l'instant) met aussi l'historique collectif à jour (`retirerMembreCollectifSoin`). Contrôle : `test_carnet_modifier_soin`.
- Accueil › Attendues à la traite (mobile : ligne de « À surveiller » ; PC : « Voir les N ») : ouvre une liste à CONSULTER (`renderAttenduesTraite`, une carte par brebis : motif en pastille neutre, « Depuis le … »), RIEN n'est créé ; sur chaque carte, « Mise à la traite » et « Pas traite cette campagne » (`boutonsTraiteHtml`, un geste, bandeau Annuler, comme Brebis à régulariser ; pas de « Tout mettre à la traite ») ; seul « Créer un lot avec ces animaux » (même bouton que Sous délai d'attente) crée ou rafraîchit le lot de recherche « Attendues à la traite » (`openAutoLot`). Retours : liste → Accueil ; lot créé depuis la liste → la liste (`lotSearchOrigine`) ; Sous délai d'attente ouvert depuis l'Accueil → Accueil, depuis le Carnet = onglet du Carnet (`sousDelaiOrigine`). Contrôle : `test_accueil_mobile`.
- Sous délai d'attente : un soin sans attente réelle n'y est JAMAIS (délai 0 hors bio ; en bio, délai 0 sans « minimum 48 h ») — règles uniques `delaiLaitDernierJourSoin` et `delaiViandeDernierJourSoin` (délai appliqué copié sur le soin, sinon fiche produit ; bio : doublé ou 48 h). Écran à onglets Brebis | Agnelles | Agneaux | Béliers (effectifs) : brebis = délais LAIT et VIANDE (traite, vente réforme), autres = VIANDE (`sousDelaiParAnimal`). Une carte (mobile) / une ligne (PC et PDF) par animal avec tous ses produits (type, soin, fin) et la fin la plus tardive (`libelleSoinSousDelai`). Accueil : brebis seulement, lait ou viande (`nbBrebisSousDelai`) ; Contrôle de lot (traite) : délai lait des brebis (`sousDelaiBrebisRows`) ; Export PDF et « Créer un lot » suivent l'onglet. Contrôle : `test_sous_delai`.
- Bio, « minimum 48 h » pour un délai légal de 0 : défaut par catégorie (`DEFAUT_MINIMUM_48H_BIO`) oui pour antibiotiques, antiparasitaires et anti-inflammatoires, NON pour les vaccins (exclus), « à confirmer » pour « autres » (réglable produit par produit dans Produits et délais). Contrôle : `test_pc_bio`.
- Produits sanitaires : UNE seule fenêtre de création et de modification, la fiche complète de « Produits et délais » (`ouvrirFicheProduitModal` : délais lait et viande obligatoires, 0 autorisé, ordonnance, soin au bouclage, options bio ; plus d'option « Réservé au vétérinaire » : ni case, ni vétérinaire responsable exigé au soin, la valeur déjà enregistrée n'est jamais effacée), y compris depuis une ordonnance (catégorie à choisir, jamais par défaut) ; Paramètres › Listes (mobile) : la carte « Produits sanitaires » ouvre « Produits et délais » (retour sur Listes). L'ancien écran « Gérer les produits » et sa fenêtre sont retirés ; produits et soins existants inchangés. Contrôle : `test_pc_produits_delais`.
- Rangement des produits et des soins, UN seul partout (fiche produit `ouvrirFicheProduitModal`, Carnet, Produits et délais, Paramètres › Listes ; mobile et PC) : Type (Vaccin / Traitement / Autre, segmenté `#fp-type`, obligatoire, jamais par défaut, figé en modification) puis Catégorie (`#fp-categorie`, obligatoire pour un traitement) prise dans la liste du compte avec « Ajouter… » des deux côtés : traitements = `categoriesTraitements` (dans `META_FIELDS`, Paramètres › Listes « Catégories des traitements », départ Antibiotique, Antiparasitaire, Anti-inflammatoire protégés), Autre = `categoriesSoinsAutres`. Stockage inchangé pour l'existant : Vaccin → `vaccins`, traitement de départ → sa liste historique (`CLE_PRODUITS_TRAITEMENT`), traitement ajouté et Autre → `autres` avec `produitsInfo[nom].categorieSoin` (+ `typeSoin: 'Traitement'` pour un traitement) ; une seule lecture `typeSoinProduit(nom)` ; le Carnet ne propose sous un Type + une Catégorie que les produits rangés là (`produitsDuTypeCategorie`) ; changer la catégorie d'un produit (même type) le change de liste, ses soins déjà enregistrés restent tels quels ; un traitement ajouté a sa carte « Traitement · … » dans Produits et délais et les défauts bio « à confirmer ». Contrôle : `test_categories_produits`.
- Catégories des soins « Autre » : liste de COMPTE `categoriesSoinsAutres` (dans `META_FIELDS`, Paramètres › Listes, « Ajouter… » ; départ : Vitamines et minéraux, Soin de plaie, Désinfection, Digestif et réhydratation, Homéopathie et phytothérapie, Autre ; « Soin de plaie » = valeur historique protégée). Fiche d'un produit « Autres » : « Catégorie du soin » (`produitsInfo[nom].categorieSoin`, « À choisir » tant que rien n'est choisi, jamais écrit d'office). Carnet sanitaire : la catégorie d'un soin « Autre » se choisit (prise de la fiche produit, modifiable) ; soin au bouclage : catégorie de la fiche, sinon aucune. ## Méthode de travail (consignes du propriétaire)
- Passation et décisions en suspens : `etat_avancement.md` (à lire en début de session, à tenir à jour). Dépôt PUBLIC : aucune adresse e-mail, aucun mot de passe ni aucune donnée d'élevage réelle dans le dépôt.

## Mises à jour (canal stable)
Seul un push sur `main` publie une Release (APK + installeur Windows), après la batterie de tests verte sur GitHub, et elle naît TOUJOURS en « pre-release » : l'appli installée (`derniereReleaseDisponible`) et Electron (`allowPrerelease = false`) ne proposent que les versions promues. Les autres builds (branches, lancement manuel) ne produisent qu'un artefact. Pour livrer : GitHub › Releases › modifier la version › décocher « Set as a pre-release » et cocher « Set as the latest release ». Lien à donner à un nouvel utilisateur : `…/releases/latest`. Un appareil qui n'a pas encore ce code voit encore toutes les versions : le premier build du canal stable doit être promu puis installé partout.

Canal de test (APK seulement, le PC reste stable) : un push sur une branche publie aussi une Release en pre-release, marquée « [test] » dans le nom ET « <!-- ovilog-canal-test --> » en tête du corps ; un lancement manuel ne publie rien. Le ménage du workflow ne supprime QUE les pre-releases portant ces deux marqueurs et garde les 3 plus récentes (jamais une Release de main ni une version stable). L'appli ne propose les pre-releases (`choisirReleaseMiseAJour`) qu'à un appareil de l'administrateur (`admins/<uid>`, bulle de contact) qui a activé « Recevoir les versions de test » (Paramètres › Synchro et sauvegarde, mobile, `ovilog_canal_test`, propre à l'appareil, jamais synchronisé, `canalTestActif`) ; fenêtre « Nouvelle version de test disponible » avec pastille « version de test ». Tous les autres cas ne voient que les versions promues. Contrôle : `test_canal_test` (et `test_canal_stable`).
